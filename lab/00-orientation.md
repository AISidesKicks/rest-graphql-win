# 00 Orientation

## What this lab is

One domain, four ways to reach it, and numbers for every claim.

The domain is a fictional SaaS support and billing product. Accounts buy plans, open
support tickets, receive invoices, pay them, and sometimes stop paying. That is enough
surface area for both API styles to show their real behaviour, and enough volume for the
storage engines to show theirs.

## The 2x2 matrix

|                | SQLite (OLTP)          | DuckDB (OLAP)             |
| -------------- | ---------------------- | -------------------------- |
| REST           | `/api/*`               | `/api/analytics/*`         |
| GraphQL        | `Query.*`              | `Query.analytics.*`        |

On top of that sits the agent facing layer:

- an **MCP server** at `/mcp`, one tool per operation
- a **code mode sandbox** where the model writes Python instead of calling tools one by one

## The rule that keeps the comparison honest

Everything business related lives in one service layer, `src/services/`:

```
REST routers  ──┐
                ├── services ── repositories ── SQLite
GraphQL resolvers ─┘         └──────────────── DuckDB
```

The REST routers and the GraphQL resolvers only shape the response. They never talk to
a database. So when the lab shows a difference, that difference comes from the API style
and not from two code bases that drifted apart.

## The reference business question

Almost every chapter uses the same question:

> How much revenue is at risk from accounts with an overdue invoice and open critical
> tickets?

It is a good question for a lab because it needs three resources (accounts, invoices,
tickets), it needs a join, and it needs an aggregate. REST answers it with a chain of
calls, GraphQL answers it with one query, and DuckDB answers it with one scan.

## How to run it

```bash
pixi run seed      # writes data/oltp.sqlite and data/csv/*.csv
pixi run etl       # writes data/olap.duckdb from the SQLite data
pixi run serve     # REST, GraphQL and MCP on http://127.0.0.1:8000
```

Open these three URLs:

- <http://127.0.0.1:8000/docs> - the REST reference, generated by FastAPI
- <http://127.0.0.1:8000/graphql> - GraphiQL
- <http://127.0.0.1:8000/mcp> - the MCP endpoint, it speaks JSON-RPC over HTTP

Everything runs in one pixi environment, one process and one port. That is not a
shortcut, it is the point: the lab compares API styles, so the engine, the data and the
observability have to be identical for all of them.

## The environment

```bash
pixi info | grep Name     # should print Name: apis
pixi shell                # a shell inside the environment
```

The stack:

| part | choice | why |
| ---- | ------ | --- |
| REST | FastAPI | the free `/openapi.json` is what the MCP catalog is built from |
| GraphQL | Strawberry | SDL first, GraphiQL out of the box, same process |
| OLTP | SQLite | row store, WAL mode, one writer |
| OLAP | DuckDB | column store, vectorised, cost based optimiser |
| MCP | MCP Python SDK | Streamable HTTP, mounted in the same app |
| Code mode | Pydantic Monty | Rust interpreter for a Python subset, host functions only |
| Counting | tiktoken | what the model actually pays |
| Traces | OpenTelemetry | JSONL exporter, optional OTLP for Phoenix |
| Environment | pixi | one command, one lock file |
